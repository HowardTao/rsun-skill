# 商业收入及回款预测

## 概述

按用户选择的基准日，从观远 BI 数据集 `ADS-租费分析-租赁合同台账明细`（dsId `k3a8a2772ee4143d694a2ecd`）拉取合同数据，生成收入/回款预测流程的**中间临时表**：

- **模式 A（在执行合同临时表）**：基准日当天处于在执行状态的合同——存量口径，执行流程见下文第 0-7 步。
- **模式 B（未执行合同临时表）**：起租日晚于基准日的已签约合同——增量口径，见"模式 B"一节。
- **合并步骤（执行+未执行合同清单）**：将两表按（门店, 铺位号）匹配续签关系后合并，生成"执行+未执行合同清单"，作为后续收入和回款预测的基础表，见"合并清单"一节。
- **应收明细关联步骤（合同全周期应收明细临时表 + 合并清单 34 列升级）**：按合同号关联 `ADS-租费分析-合同全周期应收明细`，生成应收明细临时表（31 列，含 12 个合同属性列与不含税金额），并把最后账期费用开始日/最后账期费用截止日/支付周期/提前收款天数四列附加到合并清单（30→34 列），见"应收明细关联与收款周期"一节。
- **续签应收预测步骤（续签合同应收明细临时表）**：按用户输入的预测年度（第 2 步确认），从合并清单筛出预测年度内到期且未续签的合同，假定正常续签，结合日单价/日净单价、支付周期、提前收款天数滚动生成续签应收明细临时表（31 列，格式与全周期应收明细一致），见"续签合同应收明细（预测）"一节。

**重要**：两个临时表及合并清单均为中间产物，**不是最终输出表**；输出列统一为 28 列 = 16 个基础列（门店名称/区域/楼栋/合同号/铺位号/租户名称/品牌/业态/主品类/楼层/计租方式/计租面积/起租日/到期日/铺位类型/合同状态）+ 6 个费用列（租金总应收/优惠后租金总应收/物业费总应收/优惠后物业费总应收/营销推广费总应收/优惠后营销推广费总应收，数据集现成字段）+ 6 个计算列（租金日单价/租金日净单价/物业费日单价/物业费日净单价/营销推广费日单价/营销推广费日净单价，元/㎡/天；**日单价 = 总应收/(到期日-起租日+1)/计租面积，日净单价 = 优惠后总应收/同口径**，保留 6 位小数；计租面积缺失/为 0、日期缺失/无效、天数为非正数时留空），均为纯明细、无汇总（合并清单另加 2 列：是否续签/续签描述）；**最终输出表后续会另行提供**。

**唯一正确口径（红线）**：在执行 = `起租日 ≤ 基准日 ≤ 到期日`（日期窗口判定）；未执行 = `起租日 > 基准日`。两种模式铺位类型默认包含**正铺+多经**；`合同状态` 字段**只展示、绝不作为筛选条件**（口径依据与验证记录见 `references/dataset-and-rules.md`）。模式 A 到期日等于基准日的合同必须包含在内。

**年度确认（收入/回款预测必问）**：执行收入和回款预测相关任务时，**必须强制询问用户要生成哪个年度的收入和回款**；默认展示当前年度（自然年，1 月 1 日 ~ 12 月 31 日），用户可自定义任意年度。用户未明确年度前不得开始生成预测结果。已编入执行流程第 2 步。

## 执行流程（模式 A：在执行合同清单）

### 第 0 步：环境前置检查（guancli，每次使用本 skill 先执行）

1. 检查 guancli 是否已安装：执行 `guancli version`（或 `which guancli`）。
2. **未安装**：参考官方文档 https://www.guandata.com/guandata-cli-installation-guide.md 安装（要求 Node.js 20+，推荐 22+）：

   ```bash
   npm install -g --foreground-scripts @guandata/guanskill
   guanskill install-skill
   ```

   安装完成后执行 `guancli auth login` 配置访问观远的凭证（部分步骤需用户在浏览器中配合完成授权；用户名密码登录时 Domain 默认 `guanbi`，也可留空自动探测）。安装/登录命令涉及系统级操作，需用户明确确认后再执行。
3. **已安装**：执行 `guancli auth status` 确认 PAT 有效；无效则执行 `guancli auth login` 重新认证。
4. 更新方式：重新执行安装命令即可（`npm install -g --foreground-scripts @guandata/guanskill && guanskill install-skill`）。
5. Python 解释器：命令模板统一使用 `~/.workbuddy/binaries/python/envs/default/bin/python`（`~` 由 shell 自动展开为当前用户主目录，不绑定具体用户名）。若本机该路径不存在（如 CodeBuddy 客户端环境），改用本机可用的 Python 3，并确保已安装 `openpyxl`（脚本唯一第三方依赖）。

### 第 1 步：确认基准日（必填）

向用户询问基准日。校验规则：

- 必须是 `YYYY-MM-DD` 格式的真实日历日期（拒绝 `2026-2-31`、`20260831`、`8月31号` 等无效/不规范输入）。
- 用户未提供、或输入无效时：明确指出问题（如"日期 2026-02-30 不存在，请输入有效日期"），引导重新输入；不要自行假设默认日期。
- 基准日晚于今日时提醒：数据集只含已签约合同，未来日期结果可能不完整。
- 基准日早于快照日很久时提醒：数据集为当前快照，历史时点的"已终止"状态无法回溯，越久远的基准日结果越不完整。

### 第 2 步：确认预估年度（收入/回款预测必填）

向用户强制询问：**要生成哪个年度的收入和回款？**

- **默认展示当前年度**（自然年，1 月 1 日 ~ 12 月 31 日），用户可自定义任意年度。
- 校验：必须是 `YYYY` 格式的真实年度（拒绝 `26 年`、`20266` 等无效/不规范输入）。
- 用户未明确年度前，不得开始生成收入/回款预测结果；仅生成合同清单等中间临时表不依赖该年度，但流程上仍统一在第 2 步先确认。

### 第 3 步：确认门店（必填）与铺位类型（可选）

- 门店：要求用户提供；口语别名按 `references/dataset-and-rules.md` 的映射转换（如"弘阳家居江北店" → `弘阳家居南京江北店`）。别名表未覆盖时用 CONTAINS 筛选去重确认全称，不要猜测。
- 铺位类型：默认不筛选（正铺+多经都包含）；仅当用户明确指定单一类型（如"只要正铺"）时才追加 `--filter "铺位类型 EQ 正铺"`。

### 第 4 步：取数

先 `guancli auth status` 确认 PAT 有效，然后执行（占位符替换后）：

```bash
guancli ds preview k3a8a2772ee4143d694a2ecd \
  --filter "门店名称 EQ <门店全称>" \
  --filter "起租日 LE <基准日> 00:00:00" \
  --filter "到期日 GE <基准日> 00:00:00" \
  --columns "门店名称,区域,楼栋,合同号,铺位号,租户名称,品牌,业态,主品类,楼层,计租方式,计租面积,起租日,到期日,铺位类型,合同状态,租金总应收,优惠后租金总应收,物业费总应收,优惠后物业费总应收,营销推广费总应收,优惠后营销推广费总应收" \
  --sort-asc 合同号 --limit 2000 -f json > /tmp/active_contracts_<基准日>.json
```

注意事项：

- 台账明细输出列 28 个：16 个基础列（含区域、楼栋）+ 6 个费用列（`租金总应收,优惠后租金总应收,物业费总应收,优惠后物业费总应收,营销推广费总应收,优惠后营销推广费总应收`）+ 6 个计算列（`租金日单价,租金日净单价,物业费日单价,物业费日净单价,营销推广费日单价,营销推广费日净单价`，由 `make_report.py` 本地计算，`--columns` 无需选取；与模式 B 完全一致）；
- 时间部分必须写 `00:00:00`（字段为零点时间戳，LE/GE 恰好构成闭区间）。
- 不要使用 `ds execute-sql`（该环境报 Spark PARSE_SYNTAX_ERROR）。
- 结果行数达到 limit 时说明可能被截断，需向用户说明并处理。

### 第 5 步：校验

读取 JSON 后核对：行数、唯一合同号数（应相等，一行一合同）；统计铺位类型分布（正铺/多经）与合同状态分布。预期会出现少量非"执行中"状态（已到期/未执行/锁定中等），这是口径的正确表现，不要剔除。

### 第 6 步：生成在执行合同临时表

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/make_report.py \
  --mode active \
  --input /tmp/active_contracts_<基准日>.json \
  --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/<门店简称>在执行合同_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

铺位类型筛选过时加 `--pos-note 正铺`（或多经）。输出为单 sheet「在执行合同」纯明细临时表（28 列，无汇总）。生成后用 present_files 交付，并向用户说明这是中间临时表、最终输出表后续提供。

### 第 7 步：汇报

在回复中给出：合同总数、正铺/多经分布、计租面积合计、起租日/到期日范围、到期分布（重点提示基准日后 30/90 天内到期的份数）、口径说明与快照时间。

## 模式 B：未执行合同临时表（收入/回款预测输入）

口径：**未执行 = 起租日 > 基准日**（即已签约但尚未起租的合同，`起租日 GT <基准日> 00:00:00`）**且 起租日 < 到期日**（剔除起租日≥到期日或日期缺失/无效的异常记录；guancli filter 不支持字段间比较，该条件由 `make_report.py --mode future` 在本地过滤，脚本会打印剔除明细）；`合同状态` 只展示不筛选；铺位类型默认正铺+多经（用户指定单类型时同模式 A 处理）。前置步骤（第 0-3 步：guancli 检查、基准日确认、预估年度确认、门店确认）与模式 A 完全相同。

### 取数

```bash
guancli ds preview k3a8a2772ee4143d694a2ecd \
  --filter "门店名称 EQ <门店全称>" \
  --filter "起租日 GT <基准日> 00:00:00" \
  --columns "门店名称,区域,楼栋,合同号,铺位号,租户名称,品牌,业态,主品类,楼层,计租方式,计租面积,起租日,到期日,铺位类型,合同状态,租金总应收,优惠后租金总应收,物业费总应收,优惠后物业费总应收,营销推广费总应收,优惠后营销推广费总应收" \
  --sort-asc 起租日 --limit 2000 -f json > /tmp/future_contracts_<基准日>.json
```

输出列与模式 A 完全一致（统一 28 列临时表）。其余注意事项同模式 A（`00:00:00`、不用 `execute-sql`、limit 截断提醒）。

### 生成临时表

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/make_report.py \
  --mode future \
  --input /tmp/future_contracts_<基准日>.json \
  --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/<门店简称>未执行合同_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出为单 sheet「未执行合同」纯明细临时表：首行表头、一行一合同、冻结首行、带自动筛选，**无任何汇总**，与在执行合同临时表规格完全一致，共同作为后续收入和回款预测的基表输入。生成后用 present_files 交付，并向用户说明这是中间临时表、最终输出表后续提供。

### 校验与汇报

核对行数与唯一合同号数（应相等，一行一合同）；检查脚本打印的"已过滤"信息，若有剔除需向用户说明剔除行数及原因（起租日≥到期日或日期缺失/无效）。在回复中给出：合同总数、起租日范围（最早/最晚起租日）、铺位类型分布、计租面积合计、口径说明（起租日>基准日 且 起租日<到期日 的未执行合同）与快照时间。

## 合并清单（执行+未执行合同清单，收入/回款预测基础表）

在模式 A、B 的两个取数 JSON 都已落盘后执行（输入直接用 `/tmp/*.json`，无需先生成各自的 xlsx）。

### 续签判定规则

同一（门店名称, 铺位号）下，在执行合同与未执行合同同时存在即视为续签关系：

- 在执行合同（原合同）：`是否续签` = `是`；`续签描述` = `合同已续签，续签合同号：<未执行合同号>`
- 未执行合同（新合同）：`是否续签` = `否`；`续签描述` = `该合同为续签合同，续签自合同号：<在执行合同号>`
- 无续签关系的其余合同：`是否续签` = `否`；`续签描述` 为空。
- 同一铺位有多份合同时，按起租日升序列出全部合同号（顿号分隔）；铺位号为空的记录不参与匹配，按无续签处理。

### 合并命令

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/merge_contracts.py \
  --active /tmp/active_contracts_<基准日>.json \
  --future /tmp/future_contracts_<基准日>.json \
  --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/执行+未执行合同清单_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出为单 sheet「执行+未执行合同清单」：30 列 = 28 列基础列（含区域、楼栋、6 个费用列与 6 个日单价计算列）+ `是否续签` + `续签描述`。按铺位号、起租日、合同号排序（同铺位下在执行合同起租日必然早于未执行合同，续签合同对自然相邻便于核对）。该清单为**临时文件**，是后续收入和回款预测的基础表（后续关联的应收明细均为存量收入，无需区分合同来源列）；最终输出表后续另行提供。生成后用 present_files 交付。

> **输出路径约定**：所有中间临时表 xlsx（在执行/未执行合同、合并清单、应收明细、续签明细）一律输出到**用户当前工作目录**（即 AI 执行命令时所在的项目目录，**不是技能安装目录**）下的 `output/` 文件夹，命名 `<门店简称><表名>_<基准日>.xlsx`；**禁止写入技能安装目录**——技能可能安装在 `~/.workbuddy/skills/` 等位置，运行产物应留在用户自己的工作区。它们均不是最终报告，最终输出表后续另行提供。

### 校验与汇报

核对：总行数 = 在执行行数 + 未执行行数；续签铺位的合同在两表中成对出现。在回复中给出：在执行/未执行合同数、已续签份数（在执行侧）、续签合同份数（未执行侧）、非续签的未执行合同数、口径与快照时间。

## 应收明细关联与收款周期（合同全周期应收明细临时表 + 合并清单 34 列升级）

在模式 A、B 取数 JSON 落盘且应收明细分批 JSON 取回后执行。数据源：`ADS-租费分析-合同全周期应收明细`（dsId `ud1f309f6e04d4285b7364c4`，一行一账单费用区间明细），与合同清单**按合同号关联**，费用类型四类（租金/物业费/营销推广费/其他费用）**全部纳入**。

### 第 1 步：分批取数（按合同号 IN）

从两个清单 JSON 提取全部唯一合同号，按 50 个/批用 `合同号 IN` 取数（单批最大观察值约 4,200 行，`--limit 10000` 安全；合同号超 200 个时按此法分批）：

```bash
# 提取合同号并分批
python -c "import json; ids=sorted({str(r.get('合同号') or '').strip() for p in ['/tmp/active_contracts_<基准日>.json','/tmp/future_contracts_<基准日>.json'] for r in json.load(open(p)) if str(r.get('合同号') or '').strip()}); open('/tmp/contract_ids_<基准日>.txt','w').write('\n'.join(ids))"
mkdir -p /tmp/receivable_batches_<基准日> && split -l 50 /tmp/contract_ids_<基准日>.txt /tmp/receivable_batches_<基准日>/b_
# 每批取数（zsh 下循环）
for f in /tmp/receivable_batches_<基准日>/b_*; do
  ids=$(paste -sd, - "$f")
  guancli ds preview ud1f309f6e04d4285b7364c4 \
    --filter "合同号 IN $ids" \
    --columns "门店名称,合同号,铺位号,租户名称,应收编号,账单主键,费用名,费用类型,税率,费用开始日,费用截止日,应收日,应收金额,优惠金额,优惠后应收金额,已收金额,未收金额" \
    --sort-asc 合同号 --limit 10000 -f json > "/tmp/receivable_batches_<基准日>/$(basename $f).json"
done
```

注意：合同号同时存在纯数字（如 `000009777`）与 `HYGC-*` 两种格式，均可直接 IN 匹配；`其他费用` 含能源费（后付）与保证金等，账单时间结构异于租金，只展示、不做筛选。

### 第 2 步：生成应收明细临时表 + 合并清单 32 列

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/receivable_detail.py \
  --active /tmp/active_contracts_<基准日>.json \
  --future /tmp/future_contracts_<基准日>.json \
  --receivable "/tmp/receivable_batches_<基准日>/b_*.json" \
  --base-date <基准日> --store <门店全称> \
  --output-detail <工作目录>/output/<门店简称>合同全周期应收明细_<基准日>.xlsx \
  --output-merged <工作目录>/output/执行+未执行合同清单_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出 1（应收明细临时表，单 sheet 纯明细 31 列）：

- 合同标识 + 合同属性 16 列：门店名称/合同号/铺位号/租户名称 + 区域/楼栋/品牌/业态/主品类/楼层/计租面积/起租日/到期日/铺位类型/合同状态/是否续签（12 个合同属性列按合同号取自合并清单；区域/楼栋为台账字段、随清单输入）；账单标识 2 列：应收编号/账单主键；费项 3 列：费用名/费用类型/税率；时间周期 3 列：费用开始日/费用截止日/应收日；含税金额 5 列：应收金额/优惠金额/优惠后应收金额/已收金额/未收金额。
- 不含税计算 2 列：**不含税应收金额 = 应收金额/(1+税率)**、**不含税优惠后应收金额 = 优惠后应收金额/(1+税率)**（价税分离，税率缺失时留空，保留 2 位小数）。
- 脚本内部按账单主键去重并过滤到清单合同号；按合同号/费用类型/费用开始日排序。

输出 2（合并清单 34 列）= 30 列 + `最后账期费用开始日` + `最后账期费用截止日` + `支付周期` + `提前收款天数`：

- **最后账期** = 费用类型为「租金」的账单中费用截止日最晚一期（截止日相同时取费用开始日更晚，再同取应收日更晚）。
- **最后账期费用开始日 / 最后账期费用截止日** = 该期账单的费用开始日 / 费用截止日。
- **支付周期** = 费用截止日 − 费用开始日 + 1（天）；**提前收款天数** = 费用开始日 − 应收日（天，负数表示后付，如实展示）。
- 无租金账单的合同四列留空；对应日期缺失/无效时相应列留空。

### 校验与汇报

核对：应收明细行数 = 各分批 JSON 行数之和（无去重/过滤时）；覆盖合同数 / 清单合同数；合并清单 34 列、行数 = 在执行 + 未执行（过滤后）。在回复中给出：费用类型分布、金额合计（应收/优惠后/不含税/已收/未收）、最后账期起止日/支付周期常见值、提前收款天数范围与后付合同数、无明细/无租金账单的合同清单、口径说明与快照时间。

## 续签合同应收明细（预测年度，假定续签的滚动应收预测）

前置：合并清单（34 列）已生成（应收明细临时表仅作校验对照，非本步骤输入）。**预测年度取第 2 步确认的预估年度**（默认当前年度，用户可自定义）。

### 口径（2026-09-08 用户确认）

- **候选合同**：合并清单中**到期日落在预测年度内**且**是否续签 = 否**的合同（在执行+未执行均含）；`是否续签 = 是` 的合同已有真实续签合同，**不生成**假定续签明细。
- **滚动规则**：续签期从原合同**到期日 +1** 起，按合同**支付周期**连续切账期（账期长度 = 支付周期天数，跨年账期完整生成不截断）；**应收日 = 费用开始日 − 提前收款天数**，**应收日落在预测年度内的账期才生成**；应收日早于预测年度的账期跳过（回款属上一年度）但滚动继续；应收日晚于预测年度即停止。
- **费项与金额**：租金/物业费/营销推广费三类，各用清单中的日单价/日净单价（元/㎡/天）；应收金额 = 日单价 × 计租面积 × 账期天数、优惠后应收金额 = 日净单价 × 计租面积 × 账期天数、优惠金额 = 应收 − 优惠后；**已收金额 = 0、未收金额 = 优惠后应收金额**（预测行视为全部未回款）；日单价缺失的费项跳过。
- **税率（2026-09-08 调整为固定费项税率，不再取历史账单税率）**：**租金 = 9%、物业费 = 6%、营销推广费 = 6%**；不含税两列按该固定税率计算。
- **账单标识**：应收编号留空；账单主键 = 虚拟 ID `XC-<合同号>-<4位序号>`；费用名 = 费用类型同名（租金/物业费/营销推广费）。
- **跳过并单独汇报**：支付周期/提前收款天数缺失的合同、三费项日单价或计租面积缺失的合同、应收日不落在预测年度的合同。

### 命令

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/renewal_receivable.py \
  --merged <工作目录>/output/执行+未执行合同清单_<基准日>.xlsx \
  --forecast-year <预测年度> --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/<门店简称>续签合同应收明细_<预测年度>年_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出为单 sheet「续签合同应收明细」纯明细临时表：**31 列与合同全周期应收明细格式完全一致**（含 12 个合同属性列，按合同号取自合并清单；起租日/到期日/合同状态为原合同值），按合同号/费用类型/费用开始日排序；同样是中间临时表，非最终输出表。

### 校验与汇报

核对：生成行数与覆盖合同数；抽样复核金额 = 日单价 × 计租面积 × 天数、税率按费项固定值（租金 9%/物业费 6%/营销推广费 6%）；应收日范围应在预测年度内。在回复中给出：候选合同数（在执行/未执行拆分）、已续签排除数、生成行数与覆盖合同数、应收日范围、金额合计（应收/优惠后/不含税/未收）、跳过合同清单及原因、口径说明与快照时间。
