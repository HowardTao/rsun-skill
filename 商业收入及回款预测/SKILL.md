# 商业收入及回款预测

## 概述

按用户确认的基准日与门店，从观远 BI 生成收入/回款预测流程的**中间临时表**（各表均非最终输出表，最终输出表后续另行提供）：

| # | 临时表 | 口径 / 说明 | 列数 |
|---|---|---|---|
| 1 | 在执行合同 | 起租日 ≤ 基准日 ≤ 到期日（模式 A，第 0-7 步） | 28 |
| 2 | 未执行合同 | 起租日 > 基准日 且 起租日 < 到期日（模式 B） | 28 |
| 3 | 执行+未执行合同清单 | 表 1+2 按（门店, 铺位号）匹配续签关系合并；关联应收明细后附加收款周期 4 列 | 30→34 |
| 4 | 合同全周期应收明细 | 按合同号关联应收账单（四类费用全纳入），含不含税金额 | 31 |
| 5 | 续签合同应收明细 | 预测年度内到期未续签合同假定续签，滚动生成（格式同表 4） | 31 |

### 通用约定（红线）

- **口径**：在执行 = 日期窗口判定（起租日 ≤ 基准日 ≤ 到期日，到期日=基准日的合同必须包含）；未执行 = 起租日 > 基准日。`合同状态` 字段**只展示、绝不作为筛选条件**；铺位类型默认正铺+多经，仅用户明确指定单一类型时才筛选。口径依据与验证记录见 `references/dataset-and-rules.md`。
- **必问项**：基准日（`YYYY-MM-DD` 真实日历日期）与门店必须由用户提供并确认，不得自行假设默认值；收入/回款预测必须强制确认预测年度（默认当前自然年，可自定义），未明确前不得生成（见第 2 步）。
- **应收明细批次查询（强制）**：应收明细数据集（`ud1f309f6e04d4285b7364c4`，约 74.9 万行）一律按 50 个合同号/批分批取数（`--limit 10000`），达 limit 拆小重取，全部批次校验通过后方可生成；禁止一次性全量取数。详见"应收明细关联与收款周期"第 1 步。
- **取数**：一律用 `guancli ds preview --filter`（`ds execute-sql` 在该环境报 Spark `PARSE_SYNTAX_ERROR`，不可用）；日期过滤条件的时间部分必须写 `00:00:00`（字段为零点时间戳，LE/GE 构成闭区间）；`ds preview` 无 `-o` 参数，用 shell 重定向落盘 `/tmp/`；合同清单取数 `--limit 2000`，结果行数达到 limit 时向用户说明可能被截断并分批处理。
- **输出与交付**：所有中间临时表 xlsx 一律输出到**用户当前工作目录**（AI 执行时所在的项目目录，非技能安装目录）的 `output/` 文件夹，命名 `<门店简称><表名>_<基准日>.xlsx`。生成后统一用 present_files 交付，并在回复中给出校验结果、关键统计、口径说明与快照时间。
- **Python 解释器**：命令模板统一用 `~/.workbuddy/binaries/python/envs/default/bin/python`（`~` 由 shell 展开为当前用户主目录，不绑定用户名）；该路径不存在时改用本机 Python 3，并确保已安装 `openpyxl`（唯一第三方依赖）。
- **`--store` 参数（仅用于摘要）**：`--store` **不参与数据写入**，输出列的「门店名称」一律取自数据本身。四个脚本均在生成前调用 `check_store()` 做一致性校验（定义在 `make_report.py`，其余三个脚本 import 复用），`--store` 与数据实际门店不一致时打印 ⚠️ 警告（**不中断执行**），防止用 A 店取数却传 `--store B` 时摘要错标、而 Excel 内容正确却无人察觉。

### 输出列结构（模式 A/B 统一 28 列）

16 基础列（门店名称/区域/楼栋/合同号/铺位号/租户名称/品牌/业态/主品类/楼层/计租方式/计租面积/起租日/到期日/铺位类型/合同状态）+ 6 费用列（租金/物业费/营销推广费的总应收与优惠后总应收，数据集现成字段）+ 6 计算列（三费项日单价与日净单价，元/㎡/天，由 `make_report.py` 本地计算，`--columns` 无需选取；**日单价 = 总应收/(到期日-起租日+1)/计租面积，日净单价 = 优惠后总应收/同口径**，保留 6 位小数；计租面积缺失/为 0、日期缺失/无效、天数为非正数时留空）。合并清单在此基础上加 `是否续签` + `续签描述`（30 列）。

## 执行流程（模式 A：在执行合同）

### 第 0 步：环境前置检查（guancli，每次使用本 skill 先执行）

1. 检查 guancli 是否已安装：执行 `guancli version`（或 `which guancli`）。
2. **已安装**：执行 `guancli auth status` 确认 PAT 有效；无效则重新 `guancli auth login`。
3. **未安装或登录异常**：按 `references/environment-setup.md` 完成 guancli 安装与认证（目标 BI 环境 https://rsunbi.rsun.com:9521，default profile，需两个数据集的访问权限；安装/登录涉及系统级操作，需用户明确确认后再执行）。

### 第 1 步：确认基准日（必填）

- 必须是 `YYYY-MM-DD` 格式的真实日历日期（拒绝 `2026-2-31`、`20260831`、`8月31号` 等无效/不规范输入）。
- 未提供或输入无效：明确指出问题，引导重新输入，不自行假设默认日期。
- 基准日晚于今日：提醒数据集只含已签约合同，未来日期结果可能不完整。
- 基准日早于快照日很久：提醒数据集为当前快照，历史状态无法回溯，结果越早越不完整。

### 第 2 步：确认预估年度（收入/回款预测必填）

- 强制询问：**要生成哪个年度的收入和回款？** 默认展示当前自然年（1 月 1 日 ~ 12 月 31 日），用户可自定义任意年度；必须是 `YYYY` 格式的真实年度（拒绝 `26 年`、`20266` 等）。
- 用户未明确年度前，不得开始生成收入/回款预测结果；仅生成合同清单等中间表不依赖年度，但流程上仍统一在第 2 步先确认。

### 第 3 步：确认门店（必填）与铺位类型（可选）

- 门店：要求用户提供；口语别名按 `references/dataset-and-rules.md` 映射转换（如"弘阳家居江北店" → `弘阳家居南京江北店`）；别名表未覆盖时用 CONTAINS 筛选去重确认全称，不猜测。
- 铺位类型：默认不筛选（正铺+多经都包含）；仅用户明确指定单一类型（如"只要正铺"）时才追加 `--filter "铺位类型 EQ 正铺"`。

### 第 4 步：取数

先 `guancli auth status` 确认 PAT 有效，然后执行（占位符替换后）：

```bash
guancli ds preview k3a8a2772ee4143d694a2ecd \
  --filter "门店名称 EQ <门店全称>" \
  --filter "起租日 LE <基准日> 00:00:00" \
  --filter "到期日 GE <基准日> 00:00:00" \
  --columns "门店名称,区域,楼栋,合同号,铺位号,租户名称,品牌,业态,主品类,楼层,计租方式,计租面积,起租日,到期日,铺位类型,合同状态,租金总应收,优惠后租金总应收,物业费总应收,优惠后物业费总应收,营销推广费总应收,优惠后营销推广费总应收" \
  --sort-asc 合同号 --limit 2000 -f json > /tmp/active_contracts_<基准日>.json
```

其余取数注意事项（execute-sql 不可用、`00:00:00`、limit 截断）见"通用约定"；6 个日单价计算列由脚本本地生成，`--columns` 无需选取。

### 第 5 步：校验

读取 JSON 后核对：行数、唯一合同号数（应相等，一行一合同）；统计铺位类型分布（正铺/多经）与合同状态分布。预期会出现少量非"执行中"状态（已到期/未执行/锁定中等），这是口径的正确表现，不要剔除。

### 第 6 步：生成在执行合同临时表

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/make_report.py \
  --mode active \
  --input /tmp/active_contracts_<基准日>.json \
  --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/<门店简称>在执行合同_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

铺位类型筛选过时加 `--pos-note 正铺`（或多经）。输出为单 sheet「在执行合同」纯明细临时表（28 列，首行冻结、自动筛选、无汇总）。

### 第 7 步：汇报

在回复中给出：合同总数、正铺/多经分布、计租面积合计、起租日/到期日范围、到期分布（重点提示基准日后 30/90 天内到期的份数）。

### 校验与汇报

核对行数与唯一合同号数（应相等，一行一合同）；检查脚本打印的"已过滤"信息，若有剔除需说明行数及原因（起租日≥到期日或日期缺失/无效）。在回复中给出：合同总数、起租日范围（最早/最晚）、铺位类型分布、计租面积合计。

## 合并清单（执行+未执行合同清单）

在模式 A、B 的两个取数 JSON 都已落盘后执行（输入直接用 `/tmp/*.json`，无需先生成各自的 xlsx）。

### 续签判定规则

同一（门店名称, 铺位号）下，在执行合同与未执行合同同时存在即视为续签关系：

- 在执行合同（原合同）：`是否续签` = `是`；`续签描述` = `合同已续签，续签合同号：<未执行合同号>`
- 未执行合同（新合同）：`是否续签` = `否`；`续签描述` = `该合同为续签合同，续签自合同号：<在执行合同号>`
- 无续签关系的其余合同：`是否续签` = `否`；`续签描述` 为空。
- 同一铺位有多份合同时，按起租日升序列出全部合同号（顿号分隔）；铺位号为空的记录不参与匹配，按无续签处理。

### 合并命令

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/merge_contracts.py \
  --active /tmp/active_contracts_<基准日>.json \
  --future /tmp/future_contracts_<基准日>.json \
  --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/执行+未执行合同清单_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出为单 sheet「执行+未执行合同清单」：30 列（28 列基础列 + `是否续签` + `续签描述`），按铺位号、起租日、合同号排序（续签合同对自然相邻便于核对）。该清单为后续收入和回款预测的基础表；不设合同来源列（后续关联的应收明细均为存量收入）。

### 校验与汇报

核对：总行数 = 在执行行数 + 未执行行数；续签铺位的合同在两表中成对出现。在回复中给出：在执行/未执行合同数、已续签份数（在执行侧）、续签合同份数（未执行侧）、非续签的未执行合同数。

## 应收明细关联与收款周期

数据源：`ADS-租费分析-合同全周期应收明细`（dsId `ud1f309f6e04d4285b7364c4`，一行一账单费用区间明细），与合同清单**按合同号关联**，费用类型四类（租金/物业费/营销推广费/其他费用）**全部纳入**。前置：模式 A、B 取数 JSON 落盘。

### 第 1 步：分批取数（按合同号 IN，强制批次查询）

无论合同号数量多少，一律按批次流程取数，禁止一次性全量查询：

- **切批**：从两个清单 JSON 提取全部唯一合同号，按 **50 个合同号/批**（`split -l 50`）切批；不足 50 个也按单批流程落盘到批次目录，保持路径规范统一。
- **每批命令参数固定**：`--filter "合同号 IN <本批合同号>" --columns <17 列清单> --sort-asc 合同号 --limit 10000 -f json`，落盘 `/tmp/receivable_batches_<基准日>/b_*.json`。
- **截断防护**：单批返回行数达到 limit（10000）视为可能截断，必须拆小批次重取（先试 25 个/批，仍截断继续减半），直至返回行数 < limit。
- **完整性门槛**：应得批次数 = ⌈合同号数 ÷ 50⌉；全部批次落盘且各批 JSON 可解析后，核对批次 JSON 数量与汇总行数，**校验通过才能进入第 2 步**，禁止部分批次缺失时继续执行。
- 实测经验值（689 合同号 → 14 批 → 21,613 行，单批最大约 4,200 行）见 `references/dataset-and-rules.md`。

```bash
# 提取合同号并分批
python -c "import json; ids=sorted({str(r.get('合同号') or '').strip() for p in ['/tmp/active_contracts_<基准日>.json','/tmp/future_contracts_<基准日>.json'] for r in json.load(open(p)) if str(r.get('合同号') or '').strip()}); open('/tmp/contract_ids_<基准日>.txt','w').write('\n'.join(ids))"
mkdir -p /tmp/receivable_batches_<基准日> && split -l 50 /tmp/contract_ids_<基准日>.txt /tmp/receivable_batches_<基准日>/b_
# 每批取数（zsh 下循环）
for f in /tmp/receivable_batches_<基准日>/b_*; do
  ids=$(paste -sd, - "$f")
  guancli ds preview ud1f309f6e04d4285b7364c4 \
    --filter "合同号 IN $ids" \
    --columns "门店名称,合同号,铺位号,租户名称,应收编号,账单主键,费用名,费用类型,税率,费用开始日,费用截止日,应收日,应收金额,优惠金额,优惠后应收金额,已收金额,未收金额" \
    --sort-asc 合同号 --limit 10000 -f json > "/tmp/receivable_batches_<基准日>/$(basename $f).json"
done
```

注意：合同号同时存在纯数字（如 `000009777`）与 `HYGC-*` 两种格式，均可直接 IN 匹配；`其他费用` 含能源费（后付）与保证金等，账单时间结构异于租金，只展示、不做筛选。

### 第 2 步：生成应收明细临时表（31 列）+ 合并清单升级（34 列）

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/receivable_detail.py \
  --active /tmp/active_contracts_<基准日>.json \
  --future /tmp/future_contracts_<基准日>.json \
  --receivable "/tmp/receivable_batches_<基准日>/b_*.json" \
  --base-date <基准日> --store <门店全称> \
  --output-detail <工作目录>/output/<门店简称>合同全周期应收明细_<基准日>.xlsx \
  --output-merged <工作目录>/output/执行+未执行合同清单_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出 1（应收明细临时表，单 sheet 纯明细 31 列）= 合同标识 4 + 合同属性 12（按合同号取自合并清单，区域/楼栋为台账字段随清单引入）+ 账单标识 2 + 费项 3 + 时间周期 3 + 含税金额 5 + 不含税计算 2（**不含税应收金额 = 应收金额/(1+税率)**、**不含税优惠后应收金额 = 优惠后应收金额/(1+税率)**，税率缺失留空，2 位小数）。完整列清单见 `references/dataset-and-rules.md` 及脚本 `DETAIL_COLS`；脚本按账单主键去重（无主键行按 应收编号+费用名+费用起止日 兜底）并过滤到清单合同号，按合同号/费用类型/费用开始日排序。

输出 2（合并清单 34 列）= 30 列 + `最后账期费用开始日` + `最后账期费用截止日` + `支付周期` + `提前收款天数`：

- **最后账期** = 费用类型为「租金」的账单中费用截止日最晚一期（截止日相同时取费用开始日更晚，再同取应收日更晚）；`最后账期费用开始日/截止日` = 该期账单的费用开始日/费用截止日。
- **支付周期** = 费用截止日 − 费用开始日 + 1（天）；**提前收款天数** = 费用开始日 − 应收日（天，负数表示后付，如实展示）。
- 无租金账单的合同四列留空；对应日期缺失/无效时相应列留空。

### 校验与汇报

核对：应收明细行数 = 各分批 JSON 行数之和（去重/过滤前）；覆盖合同数 / 清单合同数；合并清单 34 列、行数 = 在执行 + 未执行（过滤后）。在回复中给出：费用类型分布、金额合计（应收/优惠后/不含税/已收/未收）、最后账期起止日/支付周期常见值、提前收款天数范围与后付合同数、无明细/无租金账单的合同清单。

## 续签合同应收明细（预测年度）

前置：合并清单（34 列）与合同全周期应收明细临时表均已生成；**预测年度取第 2 步确认的预估年度**。

### 口径

- **候选合同**：合并清单中**到期日落在预测年度内**且**是否续签 = 否**的合同（在执行+未执行均含）；`是否续签 = 是` 的合同已有真实续签合同，不生成。
- **滚动规则**：续签期从原合同**到期日 +1** 起，按合同**支付周期**连续切账期（账期长度 = 支付周期天数，跨年账期完整生成不截断）；**应收日 = 费用开始日 − 提前收款天数**，**仅生成应收日落在预测年度内的账期**——应收日早于预测年度的账期跳过（回款属上一年度）但滚动继续；应收日晚于预测年度即停止。
- **费项与金额**：租金/物业费/营销推广费三类，各用清单中的日单价/日净单价（元/㎡/天）：应收金额 = 日单价 × 计租面积 × 账期天数、优惠后应收金额 = 日净单价 × 计租面积 × 账期天数、优惠金额 = 应收 − 优惠后；**已收金额 = 0、未收金额 = 优惠后应收金额**（预测行视为全部未回款）；日单价缺失的费项跳过。
- **税率（固定费项税率，不取历史账单税率）**：租金 = 9%、物业费 = 6%、营销推广费 = 6%；不含税两列按此计算。
- **账单标识**：应收编号留空；账单主键 = 虚拟 ID `XC-<合同号>-<4位序号>`；费用名 = 费用类型同名（租金/物业费/营销推广费）。
- **跳过并单独汇报**：支付周期/提前收款天数缺失、三费项日单价或计租面积缺失、应收日不落在预测年度的合同。

### 命令

```bash
~/.workbuddy/binaries/python/envs/default/bin/python <skill目录>/scripts/renewal_receivable.py \
  --merged <工作目录>/output/执行+未执行合同清单_<基准日>.xlsx \
  --forecast-year <预测年度> --base-date <基准日> --store <门店全称> \
  --output <工作目录>/output/<门店简称>续签合同应收明细_<预测年度>年_<基准日>.xlsx \
  --snapshot-time "<ds get --brief 查到的更新时间>"
```

输出为单 sheet「续签合同应收明细」纯明细临时表：**31 列，与合同全周期应收明细格式完全一致**，按合同号/费用类型/费用开始日排序。

### 校验与汇报

核对：生成行数与覆盖合同数；抽样复核金额 = 日单价 × 计租面积 × 天数、税率按费项固定值（租金 9%/物业费 6%/营销推广费 6%）；应收日范围应在预测年度内。在回复中给出：候选合同数（在执行/未执行拆分）、已续签排除数、生成行数与覆盖合同数、金额合计（应收/优惠后/不含税/未收）、跳过合同清单及原因。
